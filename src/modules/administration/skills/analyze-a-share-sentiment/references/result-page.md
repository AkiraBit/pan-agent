# 情绪周期综合看板

目标是用户提供的结果页：读完知道今天是什么状态、为什么、明天等什么、关注谁、什么情况下取消计划。不要把研究日志、接口诊断或待用户自行判断的材料当作结果。

## 固定内容顺序

### ① 结论区

- **今日评价**：简短节奏标签 + 一句裁决。例如“退潮延续：封板局部改善，但跌停扩散与接力收缩仍主导盘面”。示例只展示句式，不是当前行情。
- **周期定位**：沿用低迷/冰点、修复、发酵/扩张、高热、分歧、退潮六阶段，可落在相邻阶段之间。只在历史记录足以支持时写起始日和持续天数。
- **短线情绪**：当前强弱、相对昨日变化；明确局部反弹有没有转成普遍赚钱效应。
- **指数·趋势端**：主要指数涨跌、成交变化、强弱板块，少量关键数字嵌入结论。
- **盘面关键变化**：跌停、封板率、一进二、高度和梯队的前值→现值；不要把“封板率上升”直接判为全面修复。
- **板块与承接**：直接判断哪条线有持续性、哪条是防御、哪条只是个股独立强。板块排名靠前但指数为负时称相对抗跌。
- **今日应对 / 买点判定**：明确等待、回避追高或条件观察，说明主要理由；没有账户数据就不写用户实际仓位和成交。

### ② 明日预判

一行标题给出下一交易日主要矛盾；正文给基准情景。随后分别列左侧/右侧触发与失效条件，以及 3—6 项“明日边界”：

- 周期延续 / 证伪；
- 高标与梯队；
- 主线延续或轮动；
- 承接质量；
- 右侧确认；
- 龙虎榜只有值得强调的真实差异时才加入，不硬凑“硬信号”。

每项都要写“若什么实际变化发生 → 怎么改判或行动”。条件可以引用本次实际值作为比较基准，不照抄截图中的固定数字。不写空泛的“关注资金、注意风险”。

### ③ 明日操作与买点聚焦

先给 2—5 条简短操作计划，再分左侧与右侧路径。每条包含触发、取消、动作、板块、最多 3 只核心候选。

每只候选必须有：股票名/代码、身份（最高板、板块核心、低位承接等）、选择理由、具体关注条件、取消条件。来自实际数据池，不能靠模型记忆补造名称、涨停、排名或龙虎榜金额。

没有合适候选就明确等待。参考图中的个股、日期、仓位只是样例，不继承为本次结果。普通 A 股新买入部分不能当日卖出；因此把盘中失效写成取消未成交计划或停止加仓，已持仓处置按可卖数量及下一可卖时点处理。不把回封后的确认倒填成回封前低点成交。

上述制度要求用于内部检查，正文只写具体操作，不重复讲“不能回填成交”等取证规则。价格与点位最多保留两位小数，并说明是当日收盘价、高点或其他实际参照。

### ④ 情绪数据

少量卡片与连板梯队补足正文，不再次铺开全部证据。页尾只有一个默认折叠的“数据来源与判断依据”，逐项保留来源、时点、口径和原始数据。修订记录、研究状态与参数备注也只放在详情，不占据日常结果主体。

## 现有数据的取用顺序

1. 长桥 `trading_days` 确定最新交易日；`screener_search` + `quote` 得到股票广度及指数快照。筛选目录不代替报价。
2. 扶摇 `get_a_share_special_data_limit_up_pool / limit_down_pool / limit_break_pool` 明确请求交易日并完整分页；`limit_up_statistics` 同时取当日、上一交易日。供应商统计与剔除 ST 后的队列分别保留分母。
3. `limit_up_ladder` 有近 30 个交易日梯队。上一日涨停池按股票名单和精确板数，与当日池逐股交叉计算一进二等晋级；不把“5板以上”合并档位当精确5板。
4. `get_a_share_prices_historical_batch` 获取昨日涨停股当日反馈、当前候选近日日线；使用同一代码与相邻有效交易日，分主板/创业板/科创板/北交所统计。当前长桥报价也可用于同日盘中反馈。
5. `get_a_share_index_catalog_ths_index_list` 分概念/行业全量枚举；`get_a_share_index_prices_snapshot` 比较当日排名；`get_a_share_index_prices_historical_batch` 判断重点板块和指数近期走势。使用真实板块指数，不用今天成分重建历史板块收益。
6. `get_a_share_index_constituents_ths_index_list_by_stock`、涨停原因和梯队解释当前候选角色。当前概念成员可用于最新复盘，严格历史回测另需历史成分。
7. `get_a_share_special_data_dragon_tiger_list` 作为候选佐证，按单日/多日区间分开；不是全市场资金流，也不凭净额断言资金身份或动机。

先实际调用已有接口，再判断是否缺少数据。不能因为旧版总览没有集成某接口，就要求用户再提供。若关键数据确实缺失，一次列明需要的接口/字段与影响部分，等用户补齐再生成正式页。日常条件预案不需要先拥有完整排队成交数据库；验证实盘成交或做收益回测才另需成交约束。

## 结构化输出与生成

PanWatch 的新模型输出填写 `overview.schema.json` 中 `decision`，由宿主补齐真实行情及来源，再渲染。同一 JSON 也能在 Codex 中生成独立 HTML：

```sh
python3 scripts/render_report.py --input /absolute/path/overview.json --output /absolute/path/sentiment-report.html
```

输入信封包括 `trade_date/as_of/collected_at/analyzed_at/run_id/analysis/metrics/coverage/evidence`，完整页面还包括 `next_trade_date/supplement/report_context`。`analysis.decision` 是结论与预案正文。无宿主工具时用实际取数组织相同信封，不能调用不存在的工具。最终优先交付可直接打开的结果页，不向用户堆一排技术附件链接。

## 后台保留的约束

事实、判断、情景假设分开存储；来源逐项可追溯。连续验证冻结原条件，后续修订不覆盖旧判断。数值 next_checks 仍只在下一交易日收盘验证；文字条件不冒充程序自动命中。参考图的 4200 家、65%、1/8、1.5 倍等未经独立检验，不作为默认阈值。原 1.0 研究结论不扩大到新增策略，也不在日常正文反复复述。
